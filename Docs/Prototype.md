# 三日玩法原型

本原型按已确认范围实现固定视角点击交互和按时段营业，用三天的完整流程验证“经营获取情报、情报影响行动、行动改变下一轮经营”。美术采用可替换的 uGUI 图形，内容与数值由配置驱动。

## 打开与试玩

使用团结 `2022.3.55t3` 打开仓库根目录，选择 `Game > Prototype > 1 - Create or open prototype`，再点击 Play。场景为 `Assets/_Game/Prototype/Scenes/Prototype.unity`，Game 视图建议竖屏。已有微信平台测试场景继续保留。

Windows 预览构建完成后，也可以直接运行 `Builds/PrototypeWindows/ConvenienceStore.exe`。完整构建文件夹必须一起保留，不能只复制 exe。普通运行显示欢迎说明，自动继续本机当前进度；情报日志中可重新开始。

店内可以点击三类货架、小林、许老师、广播、柜台和出口。柜台展示当前预计营业销量。底部可切换店铺、城市地图、情报日志。

## 已实现范围

| 内容 | 当前实现 |
| --- | --- |
| 单局 | 3 天，每天 3 个时段；用完自动日结 |
| 商品 | 罐头、饮用水、药品；采购、库存、两类货架、平价/高价 |
| 人物 | 小林、许老师，外加每日广播与探索中的叙事角色 |
| 对话 | 点击推进、打字效果、头像占位、长文滑动、条件选项、重复对话 |
| 地图 | 医院、校园、地铁 3 个节点，共 6 个一次性事件 |
| 情报 | NPC/广播获取；开放日期、有效期、后续事件解锁 |
| 探索反馈 | 药品、物资、医疗支援、校园互助、真相与撤离路线 |
| 结算 | 每日日结、三日成果与 3 类结果 |
| 存档 | 操作后自动保存；恢复日结/最终结果；手动保存与重开 |

## 行为规则

阅读、进货、上架/撤下、调价、地图预览都不消耗时段。营业消耗 1 时段，探索在确认事件选项时扣除该事件的时段和物资。取消预览没有代价。准备阶段可以反复思考。

只有上架的商品可以卖；最多上架两类。撤下商品保留库存。进货每次一份，每类每天供应最多 6 份，受资金限制。日结后不再允许采购或行动，进入下一天恢复供应额度。

每时段销量为库存与当前需求的较小值。高价比平价高 ¥2，每时段需求减少 1。医疗支援增加药品需求；校园互助增加罐头需求。当日需求受天气与日程影响。营业页面和柜台预览都使用同一套规则。

当前事件结果是确定性的。人物能力、装备、概率判定、伤势和随机失败尚未实现；地图上的风险文字是情境提示。

日结展示当日营业额、探索次数、资金与行动记录。三日结果按调查线索/撤离路线、社区信任/医疗支援判定。资金是现有现金，营业额不等于净利润。

## 建议的两轮试玩

第一轮偏向经营：先聊 NPC 并听广播，查看柜台预计收益，多做营业，观察医院限定机会如何过期。调整上架商品和价格，对比销量与库存变化。

第二轮偏向调查：第 1 天去医院邀请医务志愿者，再换上药品货架营业；第 2 天调查医院档案、援助校园（提前保留或采购 2 份罐头）；第 3 天听广播解锁地铁，寻找路线并接应运输。观察药品/罐头需求、后续事件与结局的变化。

建议重点反馈：是否理解剩余时段；探索的收益是否值得放弃营业；两处货架是否带来选择；事件结果是否让人愿意进入下一天。数值和文案都是原型验证值。

## 配置与复用

唯一权威编辑源为 `Configs/Prototype.json`。`Assets/_Game/Prototype/Data/Prototype.json` 是生成副本，不直接编辑。修改后运行 `Game > Prototype > 2 - Sync configuration`，再运行 `3 - Validate and run logic checks`。

| 字段 | 用途 |
| --- | --- |
| goods | 稳定商品 ID、名称、进售价和初始库存 |
| days | 每日标题、天气、说明、广播 ID、按商品顺序的需求数组 |
| npcs | 人物 ID、姓名、身份、对话 ID |
| dialogues | 对话入口、重复入口、完成标记、节点和分支选项 |
| locations.events | 事件 ID、开放日期、时段成本、所需情报、对话 ID |
| choices.effects | money / stock / flag / trust / support 的结果列表 |

对话节点有 `next` 或 `choices`；没有后续节点时结束。分支选项支持 `requiredFlag`、`forbiddenFlag` 与资源消耗。所有选项 ID 必须全局唯一；所有商品、事件、节点引用都使用稳定 ID。奖励和探索消耗由 GameSession 原子提交，DialogueRunner 只管理对话图，PrototypeApp 管理界面。

当前 UI 按三种商品、两个店内 NPC、三个地图节点与最多两个事件选项设计。增加这些数量时需要同步调整布局。可直接改文案、数值和现有节点内容；新增系统或存档结构时再升级版本。

中文字体使用独立 Noto Sans SC 子集，与平台测试字体分开。新增汉字或 UI 文案后运行 `Tools/Generate-PrototypeFont.py`（需要 fonttools 4.60.1，以及 `Logs/NotoSansSC.ttf` / `Logs/NotoSansSC-OFL.txt`），然后在编辑器重新导入并校验。字体源与许可证说明沿用 `Docs/WechatSmokeTest.md`，生成字体的 OFL 已随资源保留。

## 构建与验证

关闭同一工程的编辑器窗口后，在根目录执行：

```powershell
./Tools/Run-Prototype.ps1 -Action Setup
./Tools/Run-Prototype.ps1 -Action Validate
./Tools/Run-Prototype.ps1 -Action BuildWindows
./Tools/Run-Prototype.ps1 -Action ExportWeChat
```

微信导出位于 `Builds/WeChatPrototype/minigame/`，有 AppID 时通过 `-AppId 'wx...'` 传入。构建成功不代表真机验收通过，仍需检查触摸、安全区、中文、退出重进和前后台恢复。

逻辑校验覆盖购买事务、架位限制、调价需求、情报解锁、重复点击/事件防重、探索成本、事件过期、援助资源条件、跨日反馈、三种结果与存档恢复。完整 Windows 渲染检查由开发构建的 `-prototypeCapture` 模式执行，截图存于 `Logs/PrototypePreview`；该模式不读写玩家存档。

编辑器/Windows 使用 PlayerPrefs，微信使用 WX 同步存储。游戏使用 `convenience-store.prototype.v1` 键，与平台测试计数存档分开。存档只保存稳定状态，不恢复到中途的对话弹窗；已确认选择不会再次发奖。无法解析的旧存档会备份到 `.unreadable` 键并提示用户。

## 后续优先级

先根据两轮试玩调整需求、供给、探索成本和事件回报。随后加入人员/设施的一个明确经营作用，以及能力/装备影响事件选项的判定，再逐步扩展到 14 天。自由城市移动、顾客寻路、自由装修、多人、排行榜和商业化不属于本轮。
